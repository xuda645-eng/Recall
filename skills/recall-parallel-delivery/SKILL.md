# Recall 并行开发与统一交付

## 显式启用与作用域

- 先确认用户在当前聊天显式添加、调用或点名启用了本 Skill。仅仅创建、安装、查看、讨论本 Skill，或在引用文本中出现名称，不构成启用。
- 未启用时，不执行本 Skill 的角色分工，不把普通任务改为并行任务，不改变默认测试、提交、推送和发布规则。
- 启用仅覆盖当前聊天与用户指定的这一批任务。不自动给其他聊天添加 Skill，不修改全局配置、AGENTS.md、自动化或长期记忆以强制启用。
- 这是一项协作约定，不是文件锁、发布锁或自动隔离机制。不能声称其他聊天已受约束；提醒用户在每个参与的开发聊天中也显式添加本 Skill 并声明角色。
- 用户对本批任务的开发角色声明，明确收窄该任务原有的直接发布授权。项目安全规则和工具审批仍然有效。退出或撤销本模式不会自动发布积压提交；根据用户新的指令处理。

## 选择角色

- 用户指定“开发任务”时，只完成该任务并交接。
- 用户明确指定“集成负责人”或要求统一合并发布时，执行串行集成交付。
- 用户给出单个开发目标但未声明角色时，按开发任务处理，不自行成为集成负责人。
- 如果只添加了 Skill，没有任务、角色或集成清单，简短询问要承担哪种角色。不凭空创建任务或聊天；只有用户明确要求时才能创建新聊天。

## 工作树隔离

1. 读取当前适用的 AGENTS.md，核验 Git 根目录、有效 HEAD、当前分支、工作树和未提交改动。多源文件夹项目以实际应用仓库为准，不把父目录空仓库当作起点。
2. 每个开发任务使用独立工作树和独立任务分支，优先采用 `codex/` 前缀。复用已属于该任务的合适工作树，不切换其他工作树正在使用的分支。
3. 若当前处于共享目录或 main，在修改代码前建立自己的工作树。新任务默认从已提交的基线开始，不复制其他任务的未提交改动。已有任务的脏改动需要明确归属和安全交接，不能擅自搬迁、清理或暂存。
4. 仅修改自己的工作树。其他附加目录、父目录设计资料和原始应用目录默认作为只读参考；多个任务要修改原型时，使用各自独立副本或明确分配所有权。
5. 外部工作树的 `../prototypes` 等相对路径未必指向原资料。核验资料路径，不用指回共享代码目录的可写链接伪装隔离。依赖、测试端口、输出目录和本地测试数据也应避免互相覆盖。
6. 修改共享入口、全局样式、锁文件、数据库契约或 API 接口前，报告可能重叠的文件和接口，协调所有权；工作树防止直接覆盖，不保证合并时没有冲突。

## 开发任务

- 只实现用户分配的范围，在自己的工作树运行适用验证，并提交经过检查的任务改动。保留与本任务无关的已暂存和未暂存改动，不使用 `git add .` 混入其他任务、凭证或私人资料。
- 本任务不直接推送 main、不合并其他任务、不发布生产。不得因为项目有自动发布授权而绕过本角色限制。任务分支推送只按用户当前授权执行。
- 任务自己的发布记录使用独立文件并标明“待集成、未发布”。共享的 `docs/RELEASES.md` 索引由集成负责人统一维护，减少并行写入；这不免除任务的验证和交付记录。
- 如发现其他任务仍在改写同一共享目录或发布生产，报告冲突并协调，不宣称已经获得独占权。
- 完成后交接可核验的提交，不把“代码写完”当作“已经集成或上线”。

交接信息：

```text
角色：开发任务
任务目标与完成范围：
工作树绝对路径与分支：
基线 SHA、实现提交 SHA、交接提交 SHA：
改动文件与共享接口：
验证命令、结果、失败及未验证范围：
是否有未提交内容或未解决问题：
可能与其他任务重叠的文件、集成依赖与顺序：
任务记录路径：
发布状态：未推送 main、未部署生产
```

## 集成负责人

1. 收集用户指定任务的目标、工作树、分支、提交 SHA、验证结果和风险。核验提交可达性、所属任务、差异范围以及是否已进入 main，不猜测提交，不重复应用已有变更。信息缺失或任务未完成时，先报告并取得交接。
2. 读取当前 `docs/RELEASES.md`、`docs/DEPLOYMENT.md` 和有关产品规范。核验远端、最新 main、生产版本及其他发布者。确认本批只有一个集成发布负责人；不能确认或有另一发布正在进行时，只做无冲突的检查并先协调。
3. 在独立、干净的集成工作树和集成分支中，基于最新 main 逐个合并经过审查的固定提交。采用保持历史的 merge，必要时使用有理由且可追溯的 cherry-pick。保留所有任务的记录和有意改动，不全文件选取 ours/theirs、不重写历史、不强推。
4. 检查语义兼容性，不以“Git 没报冲突”代替审查。意图冲突时协调任务负责人或询问用户，不擅自丢弃一方功能。修改解决方案后重新验证相关行为。
5. 对集成版本重新运行必要测试、lint、类型检查、生产构建和相关 iPhone 15 PWA 验收。浏览器测试复用项目的 guarded launcher；沙箱启动失败按项目规则申请重试，不绕过保护。关键失败阻止发布，模拟测试不冒充物理手机验收。
6. 汇总任务记录并维护本次集成记录和发布索引。检查凭证、私人卡片与内部资料未进入提交。验证通过后按现有授权正常推送 main；若远端 main 在验证期间变化或推送被拒绝，检查新变更并重新集成验证，不强推，也不在推送失败后部署。
7. 仅当含应用变更时发布确切已提交、已验证的产物到既有 `recall-memory` 生产项目。部署前重新核验生产版本；若别的发布者更新了生产，停止覆盖并协调。纯 Skill、文档或本地工具变更不重新部署应用。
8. 非破坏性验证线上资源和相关流程，记录实际提交、部署 ID/URL、上一生产版本、验证和回滚边界。按项目流程以文档 follow-up 提交发布证据，不触发重复应用部署。若需回滚，确认不是覆盖别人的更新且版本兼容，遵守既有授权；不重置用户数据。

输出待集成清单、各任务集成结果、实际 main SHA、测试证据、生产发布状态和剩余问题。安装本 Skill、任务分支提交、集成成功和生产上线是不同状态，分别报告。

## 显式使用示例

在每个开发聊天中添加：

```text
$recall-parallel-delivery
角色：开发任务。本批任务：移动端优化。
我的任务：优化卡片阅读页。只在自己的工作树开发、测试并提交，完成后交接给集成负责人，不直接推送 main 或发布生产。
```

在指定的集成聊天中添加：

```text
$recall-parallel-delivery
角色：集成负责人。本批任务：移动端优化。
请集成以下已完成任务的指定提交，重新验证并统一发布。先核验交接清单和当前 Git/生产状态，不把其他聊天或未提交内容自动纳入本批。
任务清单由我提供，或从我明确指定的聊天交接中读取。
```
