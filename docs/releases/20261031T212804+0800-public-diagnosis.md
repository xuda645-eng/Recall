## Findings

### 1. Slow Public Asset Transfer Is Observed, Not An HTTP-Error Outage

Independent bounded GETs from the current Mac returned:

| Target | Result | Observed total |
|---|---|---|
| Production `sw.js` | 200, full 9595 bytes, correct JavaScript MIME | 0.99s |
| Production `assets/i18n-BAVAAYCH.js` | 200, full 174278 bytes, correct MIME | 27.55s |
| Production `icons/icon-16.png` | 200, full 601 bytes | 3.84s |
| Production registration module | 200, full decoded 5653 bytes | 5.29s |
| Production Workbox worker runtime | 200, full decoded 15112 bytes | 40.97s |
| Recorded deployment alias manifest | 200, full 621 bytes | 9.11s |
| Anonymous `/api/auth/session` | Expected 401, `Unauthorized` | 2.34s |
| Independent Cloudflare public trace control | 200, full 215 bytes | 0.48s |

The compressed module/runtime transfer sizes were 2214/5208 bytes; this is not
an explanation of uniformly good throughput. TLS/response/download timings vary
substantially between requests, consistent with the preceding SSL and partial
JS-download timeouts. Requests in this audit reached the Cloudflare LAX edge.
Read-only route inspection showed both Pages addresses and the control address
using a tunnel interface; system HTTP proxy settings were empty. No proxy, DNS,
VPN, route or credential changes were made. This evidence does not prove which
provider, tunnel, ISP, CDN path or edge is responsible; an independent network
A/B comparison has not been performed. A fast control request does not prove
that the Pages route or larger transfers are healthy.

### 2. First-Paint Dependencies Delay Registration

The complete app probe used a new isolated browser context, the real production
HTML/assets and no response replacements. Its recorded timeline:

- Document became interactive at 34.43 seconds and fired `load` at 59.04 seconds.
- At 112/122 seconds the workspace was still absent; `RichCard`, settings,
  import-related modules were pending. The anonymous 401 is expected for a fresh
  unauthenticated context, not a missing production key or database error.
- The app finally rendered and called `navigator.serviceWorker.register('/sw.js')`
  at 165.06 seconds; registration resolved and installation began at 173.34 seconds.
- At 232 seconds, the app was visible, the SW remained `installing`, there was
  no controller and the precache contained only 2 entries. No page runtime error
  or SW registration failure was observed.

Owning source: `src/components/memory-workspace.tsx` statically imports settings,
import UI and `RichCard` even for the home route, and mounts `PWAUpdatePrompt`
inside that workspace. The large RichCard JS is about 770kB uncompressed and is
present in the real first-load dependency chain. The plugin's React hook defaults
to `immediate=true`; this is not a Workbox wait-for-window-load configuration bug.
Registration cannot start through that component until its workspace dependencies
resolve and it renders. Slow transfers therefore consume the existing initial
page-load test timeout before cache installation even begins.

### 3. Full Precache Installation Adds Another Serial Network Gate

Production `sw.js` names 145 precache entries. `vite.config.ts` includes all built
JS/CSS/HTML/images/font variants and allows files up to 5MiB. The installed
Workbox `PrecacheController.install()` iterates entries and awaits each request
one at a time. An installing worker cannot claim the app until installation
completes; `clientsClaim()` does not bypass incomplete precaching.

A second, separate isolated-context diagnostic replaced only its navigation
document with an empty local diagnostic page and manually registered the real
production SW. Worker/runtime/precache requests still fetched the real public
assets. This separates worker installation from the app's slow React/module chain
and is explicitly not production-app, offline or physical-device acceptance.

It registered successfully and stayed `installing`, advancing 20 entries at
20 seconds, 42 at 50 seconds, 55 at 70 seconds and 63 at 90 seconds. The pending
resource advanced through JS modules and multiple Inter font subsets. This proves
that the worker is making serial installation progress, not failing immediately
on registration, a security policy or an incorrect root-path scope. Final bounded
counts/states are appended below; incomplete installation is not an offline pass.

The publicly downloaded Workbox runtime and registration module match the local
validated build byte-for-byte (SHA-256 comparisons). Correct MIME/full downloads
and successful registrations rule out those specific missing/corrupted-module
explanations. This does not establish that all 145 public assets were downloaded
or that a fresh production app can reopen offline.

## Conclusion And Next Actions

The observable blocker is a two-stage network wait: slow public transfers delay
the home module chain and registration, then 145 serial precache downloads delay
SW activation/control. The source's eager dependencies and broad precache magnify
an already slow/variable public path. No confirmed missing-secret, D1, wrong-MIME,
wrong-scope or Workbox-registration defect was found. The network provider-level
root cause remains unproven without a separate connection A/B test.

First compare the same public origin on an independent connection, without
changing/clearing phone data. Separately, a scoped future performance change can
defer non-home settings/import/renderer modules and start registration earlier.
Any cache-policy change must preserve installed-PWA offline and safe update
behavior and pass realistic slow-network checks; merely enlarging timeouts or
removing the offline assertion is not a fix. Do not change hosting origin, disable
certificate checks, bind a paid service or clear device caches to make tests pass.

This diagnosis changes only public documentation. No app redeploy or rollback is
required; current production and pending additive migration remain untouched.
